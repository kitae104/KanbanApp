# Kanban App — 사용자 로그인과 보드 소유권 명세 (Spec)

## 1. Original Requirements (원문)

> 1. 이메일/패스워드 로그인을 제공하고 유저마다 1개의 칸반보드를 가질 수 있다.
> 2. 유저는 자신이 갖고 있는 칸반보드에 대한 아이템만 읽기, 쓰기, 삭제할 수 있다.

## 2. Overview (개요)

지금 칸반 보드는 로그인 없이 브라우저 `localStorage`에 보드 1개를 저장한다. 이번 작업에서는 **이메일/패스워드 계정**을 도입한다. 보드와 카드는 서버에 저장하고, 모든 보드와 카드에 **소유자(유저)** 를 둔다.

- 유저 한 명은 보드를 정확히 1개 가진다.
- 유저는 자기 보드의 카드(아이템)만 조회·생성·수정·이동·삭제할 수 있다.
- 다른 유저의 카드는 ID를 알더라도 읽거나 바꿀 수 없다. 권한 검사는 **서버에서** 한다.

기존 보드 UI(3개 고정 컬럼, Drag & Drop, 카드 CRUD, 접근성, 저장 실패 시 롤백)는 그대로 두고, 저장소와 접근 제어만 바꾼다.

## 3. Goals (목표)

- G1. 유저가 이메일과 패스워드로 회원가입, 로그인, 로그아웃할 수 있다.
- G2. 유저마다 보드가 1개 있고, 어느 브라우저나 기기에서 로그인해도 같은 보드가 보인다.
- G3. 유저는 자기 보드의 카드에만 접근할 수 있다. 다른 유저의 카드는 읽기, 쓰기, 삭제가 모두 막힌다.
- G4. 기존 보드 기능과 사용성(DnD, 키보드 조작, 오류 롤백)은 로그인한 뒤에도 똑같이 동작한다.

## 4. User Stories (사용자 스토리)

- US1. 새 사용자로서, 이메일과 패스워드로 가입하고 싶다. 가입하면 바로 빈 보드를 쓸 수 있어야 한다.
- US2. 기존 사용자로서, 이메일과 패스워드로 로그인해 내 보드를 이어서 쓰고 싶다.
- US3. 사용자로서, 공용 PC에서 쓴 뒤 로그아웃해서 다른 사람이 내 보드를 보지 못하게 하고 싶다.
- US4. 사용자로서, 다른 기기에서 로그인해도 내가 옮겨 둔 카드가 같은 위치에 있기를 바란다.
- US5. 사용자로서, 다른 사람이 내 카드를 보거나 바꾸거나 지울 수 없다는 확신이 필요하다.
- US6. 로그인하지 않은 방문자로서, 보드 주소로 들어가면 로그인 화면으로 안내받고 싶다.
- US7. 사용자로서, 이메일이나 패스워드를 틀리면 무엇이 틀렸는지 들키지 않는 일반적인 안내를 받고 싶다(계정 존재 여부 비노출).
- US8. 기존 사용자로서, 로그인 전에 이 브라우저 `localStorage`에 쌓아 둔 카드를 내 계정 보드로 가져오고 싶다.

## 5. Functional Requirements (기능 요구사항)

### 5.1 회원가입
- FR-1. 이메일과 패스워드로 회원가입한다. 이메일은 형식을 검증하고, 앞뒤 공백을 제거하고 소문자로 정규화해 저장한다. 이메일은 **유일**해야 한다.
- FR-2. 패스워드는 8자 이상 72바이트 이하이다(bcrypt 입력 한계 기준). 가입 폼에서 확인용 패스워드를 한 번 더 입력받는다.
- FR-3. 패스워드는 평문으로 저장하지 않는다. 느린 단방향 해시(argon2id 또는 bcrypt)와 유저별 salt로 저장한다.
- FR-4. 가입에 성공하면 그 유저의 빈 보드 1개가 **같은 트랜잭션에서** 만들어지고, 바로 로그인 상태가 된다.
- FR-5. 이미 가입된 이메일로 가입하면 가입을 거부하고 안내 메시지를 보여준다.

### 5.2 로그인 / 로그아웃 / 세션
- FR-6. 이메일과 패스워드로 로그인한다. 둘 중 하나라도 틀리면 "이메일 또는 패스워드가 올바르지 않습니다."라는 **같은 메시지**를 보여준다.
- FR-7. 로그인에 성공하면 서버 세션을 만들고, 세션 식별자를 `HttpOnly`, `Secure`(프로덕션), `SameSite=Lax` 쿠키로 보낸다. 세션은 7일 동안 유효하다.
- FR-8. 로그아웃하면 서버에서 세션을 무효화하고 쿠키를 지운 뒤 로그인 화면으로 이동한다.
- FR-9. 로그인하지 않은 채 보드 화면에 들어가면 로그인 화면으로 리다이렉트한다. 이미 로그인한 유저가 로그인이나 가입 화면에 들어가면 보드로 리다이렉트한다.
- FR-10. 보드 화면 헤더에 로그인한 유저의 이메일과 로그아웃 버튼을 표시한다.

### 5.3 보드 (유저당 1개)
- FR-11. 보드는 `owner_user_id`를 가지며, 한 유저에게 보드는 **최대 1개**다(DB 수준 UNIQUE). 가입 과정(FR-4)으로 만들어지므로 로그인한 유저에게는 항상 보드가 1개 있다.
- FR-12. 보드 구조는 기존과 같다. `할 일(TODO)`, `진행 중(IN_PROGRESS)`, `완료(DONE)` 3개 컬럼이 고정이다.
- FR-13. 보드 API는 보드 ID를 클라이언트에서 받지 않는다. 서버가 **세션의 유저**로 보드를 찾는다. 그래서 다른 유저의 보드를 지정하는 요청은 처음부터 만들 수 없다.

### 5.4 아이템(카드) 접근 제어
- FR-14. 카드는 소속 보드(`board_id`)를 가지고, 기존 `Card` 필드(`id`, `title` 1~100자, `description` 최대 1000자, `status`, `order`, `createdAt`, `updatedAt`)를 유지한다.
- FR-15. **읽기**: 보드 조회는 세션 유저의 보드에 속한 카드만 돌려준다.
- FR-16. **쓰기**(생성, 제목·설명 수정, 컬럼 간·컬럼 안 이동): 생성할 때는 서버가 `board_id`를 세션 유저의 보드로 정한다. 수정·이동할 때는 대상 카드가 세션 유저의 보드에 속하는지 확인한 뒤에만 반영한다.
- FR-17. **삭제**: 대상 카드가 세션 유저의 보드에 속할 때만 삭제한다.
- FR-18. 소유권 검사는 SQL 조건에 포함한다(`WHERE id = $1 AND board_id = <세션 유저의 보드>`). "조회한 뒤 확인하고 수정"하는 두 단계로 나누지 않는다(TOCTOU 방지).
- FR-19. 다른 유저의 카드 ID나 존재하지 않는 카드 ID로 요청하면 똑같이 **404**를 돌려준다. 다른 유저의 카드가 존재하는지 드러내지 않는다.
- FR-20. 한 번의 이동으로 여러 카드의 `order`가 바뀌면 하나의 트랜잭션으로 처리한다. 포함된 카드가 **모두** 세션 유저의 보드에 속할 때만 커밋한다.
- FR-21. 세션이 없거나 만료된 상태에서 보드나 카드 API를 호출하면 **401**을 돌려주고, 클라이언트는 로그인 화면으로 이동시킨다. 저장하지 못한 변경은 롤백 규칙(FR-22)을 따른다.

### 5.5 기존 동작 유지
- FR-22. 저장이 실패하면(네트워크, 서버 오류, 401, 404) 지금처럼 토스트로 알리고, 화면을 마지막으로 저장에 성공한 상태로 되돌린다.
- FR-23. 드래그 중 낙관적 업데이트는 유지하고, 서버 응답이 실패하면 롤백한다.
- FR-24. 입력 검증은 클라이언트와 서버 모두 기존 zod 스키마(`cardInputSchema`, `statusSchema`)를 사용한다.

### 5.6 기존 로컬 데이터 가져오기
- FR-25. 로그인한 유저의 보드가 비어 있고 이 브라우저 `localStorage`(`kanban-app:board`)에 유효한 데이터가 있으면, 내 보드로 가져올지 한 번 묻는다. 가져온 카드는 모두 세션 유저의 보드에 속하고, 카드 ID는 서버가 새로 발급한다. 가져오기에 성공하면 `localStorage` 원본은 백업 키로 옮긴다.

## 6. Non-Functional Requirements (비기능 요구사항)

### 보안
- NFR-1. 모든 권한 판단은 서버에서 세션을 기준으로 한다. 클라이언트가 보낸 `userId`와 `boardId`는 믿지 않는다.
- NFR-2. 로그인 시도 제한: 같은 이메일이나 IP에서 15분 동안 로그인에 10번 실패하면 일정 시간 로그인을 막는다(무차별 대입 방지).
- NFR-3. 없는 이메일로 로그인해도 해시 비교 시간을 비슷하게 맞춰, 응답 시간으로 계정 존재 여부를 알 수 없게 한다.
- NFR-4. 상태를 바꾸는 요청(POST, PATCH, DELETE)은 CSRF 방어를 한다(SameSite 쿠키와 Origin 검사, 또는 Server Action의 기본 보호).
- NFR-5. 패스워드, 해시, 세션 토큰은 로그와 오류 응답, 클라이언트 번들에 남기지 않는다. 세션 토큰은 DB에 해시로 저장한다.
- NFR-6. 모든 DB 쿼리는 파라미터 바인딩을 쓴다.
- NFR-7. 기존 CSP와 XSS 방어 테스트(`tests/e2e/security.spec.ts`)는 그대로 통과해야 한다.
- NFR-8. 세션 고정 공격을 막기 위해 로그인에 성공하면 세션 식별자를 새로 발급한다.

### 성능
- NFR-9. 카드 100개 보드 기준으로, 로그인 후 보드 첫 표시(서버 조회 포함)는 로컬 환경에서 p95 1초 이내다.
- NFR-10. 카드 이동 저장 API는 로컬 환경에서 p95 150ms 이하다. 응답을 기다리는 동안에도 드래그는 60fps를 유지한다(낙관적 업데이트).
- NFR-11. 카드 조회는 `(board_id, status, order)` 인덱스를 쓴다.

### 접근성
- NFR-12. 로그인과 가입 폼은 모든 입력에 `<label>`을 연결하고, 오류는 `aria-describedby`와 `aria-live`로 알린다. 키보드만으로 모든 조작이 가능해야 한다.
- NFR-13. 새로 추가한 화면(로그인, 가입)을 포함해 axe 기반 a11y E2E에서 위반이 0건이어야 한다.

### 사용성
- NFR-14. 패스워드 입력란에는 표시/숨김 토글을 둔다. 브라우저 자동완성 속성(`autocomplete="email"`, `current-password`, `new-password`)을 올바르게 지정한다.

## 7. Constraints & Assumptions (제약 및 가정)

### 제약
- C1. Next.js 16 (App Router)을 쓴다. 인증, 쿠키, 리다이렉트, `proxy`(구 middleware) 관련 코드를 쓰기 전에 `node_modules/next/dist/docs/01-app/02-guides/authentication.md` 등 설치된 버전의 문서를 확인한다(AGENTS.md).
- C2. 보드와 카드 데이터는 서버 쪽 영구 저장소에 둔다. 소유권을 강제하려면 서버 저장이 필요하다.
- C3. 기존 `BoardRepository` 추상화(`src/lib/storage/boardRepository.ts`)는 동기(`load`/`save`) 방식이다. 서버 저장으로 바꾸면서 비동기로 바꿔야 하고, `BoardProvider`의 저장·롤백 로직도 이에 맞게 수정해야 한다.
- C4. 기존 단위·E2E 테스트는 계속 통과해야 한다. E2E는 테스트용 유저로 로그인한 상태에서 실행하도록 보완한다.

### 가정
- A1. 서버 저장소는 **PostgreSQL**(로컬 `mydb`)을 쓰고, 개발 중 스키마·데이터 확인은 postgres MCP로 한다고 가정한다(이 브랜치 이름과 앞선 대화 기준). 저장소와 인증 라이브러리의 최종 선택은 `/sdd:plan`에서 정한다.
- A2. 보드는 개인용이다. 보드 공유, 팀, 권한 역할(편집자·뷰어)은 범위 밖이다.
- A3. 이메일 인증 메일, 패스워드 재설정, 소셜 로그인(OAuth), 2단계 인증은 이번 범위에 넣지 않는다. 다만 나중에 추가할 수 있게 유저 테이블에 `email_verified_at` 같은 확장 여지를 둔다.
- A4. 회원 탈퇴는 범위 밖이다. 나중에 탈퇴 기능을 넣을 때는 유저를 지우면 보드와 카드도 함께 삭제(CASCADE)되도록 설계한다.
- A5. 실시간 동기화(다른 기기의 변경을 바로 반영)는 범위 밖이다. 다른 기기의 변경은 새로고침하면 보인다.
- A6. 관리자가 다른 유저의 보드를 보는 기능은 없다. 어떤 계정도 다른 유저의 아이템에 접근할 수 없다.

## 8. Success Criteria (성공 기준)

- SC-1. 새 이메일로 가입하면 곧바로 빈 보드가 보이고, DB에 유저 1건과 그 유저의 보드 1건이 생긴다.
- SC-2. 같은 이메일(대소문자나 앞뒤 공백만 다른 경우 포함)로 다시 가입하면 거부된다.
- SC-3. 틀린 패스워드와 없는 이메일에 똑같은 오류 메시지가 나온다.
- SC-4. 로그아웃한 뒤 보드 URL에 들어가면 로그인 화면으로 이동하고, 보드와 카드 API는 401을 돌려준다.
- SC-5. **격리 테스트**: 유저 A와 B가 각각 카드를 만든다. B의 세션으로 A의 카드 ID를 조회, 수정, 이동, 삭제하면 모두 404이고, A의 카드는 DB에서 전혀 바뀌지 않는다. B의 보드 조회 결과에는 A의 카드가 하나도 없다.
- SC-6. 여러 카드가 함께 옮겨지는 요청에 다른 유저의 카드 ID가 하나라도 섞이면 요청 전체가 거부되고 DB에 부분 반영이 남지 않는다.
- SC-7. 유저 A가 브라우저 두 개(또는 `localStorage`를 비운 브라우저)에서 로그인하면 같은 보드와 순서가 보인다.
- SC-8. DB의 패스워드 컬럼에는 해시만 있고, 평문 패스워드나 세션 토큰 원문은 어디에도 저장되지 않는다.
- SC-9. 로그인에 11번째로 실패하면 시도 제한 메시지가 나온다.
- SC-10. 기존 기능 E2E(카드 CRUD, DnD, 키보드 이동, 저장 실패 롤백, a11y, CSP)가 로그인한 상태에서 모두 통과한다.
- SC-11. `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e`가 모두 통과한다.
